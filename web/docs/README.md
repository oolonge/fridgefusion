# Проект FridgeFusion: Обзор и архитектурные принципы

## Основная идея проекта

FridgeFusion — это интеллектуальная платформа для подбора рецептов на основе имеющихся у пользователя продуктов. Система позволяет:
- Вести учет продуктов в "виртуальном холодильнике"
- Получать рекомендации рецептов на основе доступных ингредиентов
- Фильтровать рецепты по различным параметрам (диетические ограничения, время приготовления и т.д.)
- Сортировать рецепты по доступности (с учетом заменяемости ингредиентов)
- Управлять профилем пользователя

## Архитектурные решения

Проект реализован с использованием **луковичной "чистой архитектуры"** с четкими слоями и разделением ответственности:

1. **Доменный слой (domain)** — ядро системы:
   - Бизнес-сущности (Recipe, Ingredient, User, Fridge, FridgeItem и др.)
   - Объекты передачи данных (DTO)
   - Не имеет зависимостей от других слоев

2. **Слой приложения (application)** — бизнес-логика:
   - Процессоры (IRecipeExplorerProcessor, IFridgeProcessor, IUserProcessor, IAuthProcessor)
   - Сервисы (IRecipeFilterService, IRecipeSortingService, IIngredientService)
   - Зависит только от доменного слоя и интерфейсов инфраструктуры

3. **Инфраструктурный слой (infrastructure)** — доступ к данным:
   - Интерфейсы репозиториев
   - Реализации репозиториев (работа с PostgreSQL)
   - Конфигурация и утилиты

4. **Презентационный слой (presentation)** — пользовательский интерфейс:
   - Представления (Views)
   - Презентеры (Presenters)
   - Реализация MVP паттерна

## Ключевые принципы при реализации

При написании бизнес-логики необходимо строго соблюдать следующие принципы:

1. **Инверсия зависимостей (DIP)**:
   - Процессоры зависят от интерфейсов репозиториев, а не от их реализаций
   - Высокоуровневые модули зависят от абстракций, а не от деталей

2. **Единственная ответственность (SRP)**:
   - Каждый класс должен иметь только одну причину для изменения
   - Фильтрация, сортировка, работа с холодильником — разные ответственности

3. **Открытость/закрытость (OCP)**:
   - Код должен быть открыт для расширения, но закрыт для модификации
   - Новая функциональность добавляется через реализацию интерфейсов

4. **Чистая бизнес-логика**:
   - Никаких зависимостей от UI или конкретных технологий хранения данных
   - Бизнес-правила не должны знать о деталях представления

5. **Тестируемость**:
   - Вся бизнес-логика должна быть легко тестируема
   - Используйте внедрение зависимостей для упрощения модульного тестирования

## Важные взаимодействия

1. **Фильтрация и сортировка рецептов**:
   - RecipeExplorerProcessor координирует работу фильтрации и сортировки
   - RecipeFilterService отвечает за фильтрацию по различным параметрам
   - RecipeSortingService отвечает за сортировку с учетом доступных ингредиентов

2. **Авторизация и доступ**:
   - AuthProcessor управляет аутентификацией и авторизацией
   - Другие процессоры запрашивают информацию о текущем пользователе

3. **Работа с холодильником**:
   - FridgeProcessor обрабатывает операции с холодильником пользователя
   - RecipeSortingService использует содержимое холодильника для оценки доступности рецептов

Эта архитектура обеспечивает четкое разделение ответственности, хорошую тестируемость и гибкость для будущих изменений и расширений.
